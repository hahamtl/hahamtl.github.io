先说结论：同一个形状的 bug 第三次出现，就别再加特例了。三起"不相关"的事故，根一定在特例保护你不去看的地方：默认路径、兜底分支、else。我们花了两个月、修了三次，才把这句话说出来。

## 三起事故

第一起很小。聊天 thread 里一条回复被吞了：Agent 读了消息，判断不是它会处理的类型，就什么都没说。我们往路由表里加了这个 case。修好了。

第二起看着不一样。一个评审 Agent 被要求重新看一份上周评审过的文档。它没有重读，而是用非常具体、非常自信的理由捍卫上次的意见，而那些理由指向的内容文档里已经没有了。我们加了条规则：重新评审必须重新拉文档。修好了。

第三起又不一样。一个工程 Agent 回答代码问题时给出的文件路径和函数名根本不存在，两次，两次编的还是同一批名字。我们明明有代码搜索工具就是干这个的，它没调。正准备再加一条规则时，有人说：这和前两个是同一个 bug。

## 形状

到 Agent 的每个请求都过一个路由器。路由器有一张已知 case 表，每一行指向为它造的能力：这类消息给 thread 处理器，那类给文档评审，代码问题给代码搜索工具。表里不认识的，全部落进一个通用兜底，用模型的通识作答。

吞掉的回复：消息没匹配上，落进兜底，兜底无话可说。捍卫的文档：重评请求和评审 case 没精确匹配，落进兜底，兜底用模型记得的东西作答。编造的代码：问法出乎表的预料，落进兜底，兜底凭空写出像模像样的代码。

三个症状，一条路。我们每次修的都是往表里加一行，让某一种问法不再掉下去。没有一次碰过它们掉进去的那个地方。

## 为什么要三次

每起事故都自带一个故事。吞回复像 threading 的问题，捍卫文档像记忆的问题，编代码像幻觉。修的人不同，工单不同，每个修法在自己的 case 里都是对的。流程里没有任何一步会问"还有什么长得像这个"。

最后把它们连起来的信号很无聊：第三次的修法会和前两次是同一种修法。往同一张表里再加一行。这就是该停下来问"这张表到底是干什么的"的时刻。

## 我们改了什么

不是表。是兜底。

兜底现在多做三件事。它说出自己觉得这个请求最接近哪个能力，然后问，而不是用通识作答。请求只要碰到代码、文档或 thread，一律先走对应的工具，因为工具答"没找到"比模型凭空答要好。每一次落进兜底都带着请求形状记日志，下一个没认出来的问法就是报表里的一行，不是一起事故。

## 三次法则

我现在把同一形状的第三次出现当成和前两次不同性质的事件。一次是 bug，两次可能是巧合，三次同形状、每次都"不相关"，那就是已经有根的模式。根几乎总在特例保护你不去看的地方：默认路径、兜底、else 分支。

| | 修 case | 修兜底 |
|---|---|---|
| 工作量 | 小，局部 | 中，碰共享路径 |
| 修好的 | 这一种问法 | 所有还没见过的问法 |
| 下一次事故 | 一定来，换个故事 | 一行日志 |
| 感觉像 | 有进展 | 承认前两次没修完 |

最后一行就是为什么要等到三次。没人想重开两张已关的工单。开吧。
