一个 Agent 创建了一张工单，描述字段是空的。指令里写得很清楚：描述必填，内容是什么。工单平台没有丢字段，是 Agent 根本没发。

"创建工单"这个工具的定义里，描述字段标的是可选。说它必填的那条规则，在一个只有做某类任务时才会加载的文件里，而这次不是那类任务。两段文字冲突，Agent 相信了眼前的那段。

修法是改工具描述里的一句话。没有在别的地方再加规则。

## 接线不是重点

给 Agent 接工具，最容易有的想法是：这是接线的活。起个名，写个 Schema，把调用路由过去，完了。这篇里每一个 bug 都来自这个想法。工具定义不是接线，它是关于这个工具 Agent 一定会读到的唯一一段文字。

## 它的措辞

工具描述是模型替你签的合同。它在模型那边回答四个问题：什么时候该用我，什么时候不该用，必须传什么，会返回什么。任何你希望 Agent 每次用这个工具时都做到的事，都要写在这段文字里，因为这是它跳不过去的那段。

"可选"那个 bug 只是一个例子，模式是通用的。你的指令说"永远带上 owner"，但 Schema 没把 owner 标成必填，那 Schema 就在告诉 Agent 另一件事。在指令文件没加载的那一天，它会相信 Schema。

所以现在的规则是：什么必填、什么时候调用，写在工具自己的描述里。指令文件负责补充判断，但不持有一条硬规则的唯一副本。

## 它的沉默

工具靠"没说"出错，比靠"说错"多得多。

一个搜索工具对某个概念返回零结果，而领域专家坚持这东西存在。第一个猜测是模型幻觉，第二个是别的 thread 混进了上下文。真相是这个工具把两个词的查询理解成"两个词必须在同一行"，把整个子系统悄悄藏掉了。没报错，没警告，就是零。

另一个工具说它返回工单。多数时候是的。偶尔返回一个只有 key 的空对象，Agent 就拿着空对象当工单往下推理。

由此两条规则。自己工具返回空，不能当作"不存在"的证据：在对话里 Agent 应该说清它搜了什么；无人值守时把空结果当错误。写入之后一定读回来逐字段对比，因为一个报告成功的写入工具是在"声称"，不是在"陈述事实"。

## 它的名字

名字听起来是最不重要的部分。但恰恰是名字这里，Agent 的指令和它面对的现实会在没人注意的情况下分开。

我们的工具通过一个网关访问共享系统，网关会统一工具名：上游平台暴露的叫 `get_issue_Jira_` 之类，Agent 看到的是 `jira_get_issue`。这很合理。但这意味着一条按上游名字写的指令，指向的是一个从 Agent 视角看不存在的工具。于是 Agent 选一个听起来最像的，或者解释说做不了，或者做一件差不多的事。三种情况都发生过。

规则：工具名对着 Agent 实际看到的那个列表核对，不要对着上游文档。动词加名词，从 Agent 的视角命名，所有提到它的指令里只用同一个名字。

## 它的锁

一次安全评审发现两个内部工具网关完全没有入口鉴权。能访问到地址的任何人，都能用网关自己的凭据调后面任何工具。当时还没出过事。没出事和安全不是一回事。

修法看清了就直接：在网关鉴权一次。后面的工具继承调用者的身份，别的地方都不用再登录。它还带出一个之前跳过的问题：一次错误的调用能影响多大范围？读工具可以宽，写工具要窄，一个工具一个动作；危险的那些（删除、发送、付款）要先问，或者先写草稿。

## 把工具定义当代码来 review

| 查什么 | 问什么 | bug 长什么样 |
|---|---|---|
| 名字 | 动词 + 名词，从 Agent 视角，所有指令里一致 | Agent 调一个不存在的工具，或最像的那个 |
| 何时用、何时不用 | 是否写在描述本身 | Agent 选错工具 |
| 必填字段 | Schema 里的 required 是否等于真实规则 | 字段悄悄为空 |
| 空结果 | 描述是否说明"没找到"意味着什么 | 从零结果得出自信的答案 |
| 写入校验 | 每次写入后有没有读回 | 成功消息背后一条错记录 |
| 鉴权 | 调用者是否在同一个边界上被识别 | 网络上任何人都是 Agent |
| 影响范围 | 读宽写窄，危险动作先问或先草稿 | 一次错误调用，一大堆问题 |

这些行没有一行是关于模型的。全是关于你放在模型面前的那段文字和那道边界。
