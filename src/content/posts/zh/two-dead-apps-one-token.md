一个周五早上，两个聊天应用同时不回话了。不是同一个应用，不是同一份代码，也不是同一个团队维护。症状一模一样：打一条消息没反应，点一个按钮却好用。

两件事同时坏、症状还一样，看起来就是有共同原因。我们头几个小时都在这个思路上：平台故障、共享的配额、两个应用一起撞上限流。都不成立。两个应用身份独立，配额独立。时间上的巧合，让我们搭进去一个下午。

## 为什么越重启越糟

这两个应用用的是聊天平台的长连接模式：不是平台来调用一个公网地址，而是应用主动开一条长连接，事件从这条连接过来。一个 token，一条连接。

出事故的时候，人的本能是重启。我们重启了。每次重启把进程杀掉，但没有干净地关掉那条连接，平台那边旧连接还会挂着一阵子，新进程又开一条。一下午"再试一次"下来，一个 token 上挂了大约九条连接，平台把每个事件随机投递给其中一条。大部分是死的。打过来的消息，十条里差不多九条进了僵尸连接。

按钮之所以好用，是因为按钮点击走的是另一条路，普通的 HTTP 回调，不经过那条连接。这本该是我们第一个读懂的线索：往外发正常、按钮正常、打字进来没反应，说明问题在连接层，不在权限，不在模型，也不在处理消息的代码。

## 修法主要是停手

三个改动，都不惊险。把客户端库升到能检测"连接静默超时"的版本，不再死抱着不放。加上优雅停机，进程退出前先关掉自己的连接。然后别再动这两个应用，让僵尸连接自己过期。第二天早上两个都好了。

## 记下来的

| 本能反应 | 结果 | 应该怎么做 |
|---|---|---|
| 同时坏的两个东西有共同原因 | 搭进去一个下午 | 先确认身份和配额是不是真的共享 |
| 重启清一下 | 每次多一个僵尸 | 先看这个 token 上挂了几条连接 |
| 打字没反应就是消息处理坏了 | 查错了层 | 往外发好用 + 按钮好用 + 输入死 = 连接层 |
| 一个 token，多个进程 | 随机投递 | 一个共享 token 永远只能有一条活连接 |

最后一行成了团队里一条有名字的规矩。两个开发用同一个 token 在本地跑应用，也会撞上同样的随机投递，其中一个会花一小时纳闷为什么机器人不理他。
