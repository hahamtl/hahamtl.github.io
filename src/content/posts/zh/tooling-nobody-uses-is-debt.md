我做内部工具很多年了：测试框架、共享服务、那些大家忘了存在直到它坏掉的脚本。做久了会明白一件不太舒服的事：没人打开的工具不是免费的。它是一笔利息不高但一直在滚的债，每当它周围有东西变动，账单就到。

今年一周之内我收到了两张。

## 盘点

我们当时在把一个测试规划 Agent 从它出生的仓库搬进一个共享插件，别的团队也要安装。Agent 本体周围已经长出一小片生态：九个命令、一个进度看板、一条把反馈报告生成到仓库里的流程、一套隔离试技能的沙箱协议、几个辅助脚本。

默认方案是全部搬过去。然后有人问了唯一要紧的问题：最近三十天，这些东西各自是谁打开过？

看板：做 Agent 的我们三个。反馈流程：我们三个。沙箱协议：我们中的一个，用过两次。把工单变成测试方案的那几个命令：每个用户，每天。help 命令：所有人，一直在用，而且慢。

## 错误的假设

"全部搬"背后的假设是：已经存在的工具，留着不花钱。反正已经做出来了。

实际不是这样。你带着的每一个界面都要搬、在新家重新测、给没见过旧版的人写文档、做安全、有人被它弄糊涂时解释、底下的东西变了还要保持兼容。一个没有用户的工具把这些成本全付一遍，什么都没换回来。它还让每次迁移的体量翻倍，因为要迁的是整个面，不只是被用到的那部分。

所以我们砍了。看板、反馈流程、沙箱协议，全部砍掉。插件发出去比它来的那个仓库还小。之后几周，没有一个人问过这些东西去了哪。

## 留下的，以及对它做了什么

help 命令留下了，成了我们发出去的东西里用得最多的。它之前慢，是因为要跑一个脚本检查环境，在某些机器上还会尝试安装东西。修法是让它只打印一张静态的命令地图，别的什么都不做。秒开，简单，一天被打开几十次。整套工具里最有价值的，是做得最少的那个。

另一个留下的是安装本身。今年早些时候把一个内部服务暴露给编码助手时，我学到一件事：推广会卡在 README 上。同事用三种客户端、三种配置格式。安装做成一条命令之后，用的人才多起来。这个月插件换 marketplace，切换是四行命令，我发的就是那四行，没有发一页说明。

## 动手前的三个问题

现在我做任何内部工具之前都要先回答三个问题。三个问题没有一个是关于工具本身的。

**能不能说出一个人的名字。** 不是"团队"，不是"QA"，不是"开发"。一个具体的人，下个月会为了一件他本来就在做的事打开它。说不出名字，那我就是在给自己做。也可以，前提是我承认这一点，并且打算之后删掉。

**安装是不是一条命令。** 任何带"配置页"的东西都有一个漏斗，大部分人会从漏斗里掉出去。安装不是一行，工具就还没有发布。

**第一天有没有埋点。** 工具产出的每个 artifact 都带一个"由它产出"的标记，放在没人会编辑的字段里。这不是监控，这是唯一能不靠猜回答"最近三十天谁打开过"的办法。我之前写过的那个二月的聊天面板，这一条不及格：它还在跑，而我真的不知道有没有人在用。这是一笔我现在就背着的债。

## 反方向：最小的那个

同一年，业务方需要一个内部问答机器人。第一反应是 LLM 加检索。实际需求是查表：几十个问题，答案稳定，再加一个让非工程师能改答案的地方。

我们一天做完，一个模型都没用：聊天界面后面一张静态表，加一个编辑页。然后故意在旁边又做了一个 LLM 版本，两个并排 demo。静态那个答得更快，从不编造，答案的 owner 自己就能改。它赢了。重点不是 LLM 不适合问答，重点是能去掉摩擦的最小那个工具才是大家会一直打开的那个，而你把两个摆在人面前之前，不知道是哪个。

## 并排比较

| 界面 | 三十天内谁打开过 | 处理 |
|---|---|---|
| 工单 → 方案的命令 | 每个用户，每天 | 保留，不动 |
| help 命令 | 所有人，而且慢 | 保留，改成秒开 |
| 进度看板 | 三个开发者 | 砍掉 |
| 反馈生成流程 | 三个开发者 | 砍掉 |
| 沙箱协议 | 一个开发者，两次 | 砍掉 |
| 安装 | 所有人，一次 | 一条命令；搬家时四行 |
| 二月的聊天面板 | 不知道 | 还在跑；埋点是下一个任务 |
