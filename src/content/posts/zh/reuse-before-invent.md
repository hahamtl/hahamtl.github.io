第二个 Agent 开工那天，我列了它需要的东西：能访问工单系统、wiki 和代码托管；指令要有地方放；要能发给别人用；要能开 PR；要能读团队的测试管理工具和覆盖率数据；生成的测试要有地方落。

六项。每一项公司里都已经有人在维护一个。问题只是：给新产品单独建一套、边界清清楚楚，还是搬进已有的那套、按别人的规矩来。

我们搬了六次。九周上线。换另一条路，我不觉得二十周能上。

## 白板上，"另建一套"更好看

给新产品画架构，最有吸引力的画法是自己单独一列：自己的集成层、自己的仓库、自己的发布流水线，整齐地立在已有系统旁边。每个框都归你管，你做什么都不会影响别人。

但每个框也都是你要运维的一个系统。要凭据、要监控、坏了要有人接、底下的东西一动就要迁移。而且第二列和第一列是重复的，任何改进要么做两遍，要么不做。

## 六次当租户

| Agent 需要 | 没做的 | 用了已有的 | 实际写的 |
|---|---|---|---|
| 访问工单、wiki、代码 | 自己的连接器 | 第一个 Agent 已经在用的集成网关，通过 MCP 暴露 | 指令里的工具名，别的没有 |
| 放指令的地方 | 自己的仓库 | 共享技能库，和其他 Agent 的技能同一个目录 | 几份 markdown |
| 发布 | 自己的流水线 | 一个已有插件和它的 marketplace，作为新增的一组命令 | 升一个版本号，写一条 changelog |
| 开 PR | 一个 PR 步骤 | 插件里已有的建 PR 技能，整个委托给它 | 零行 |
| 测试用例和覆盖率 | 自己的存储 | 团队的测试管理工具，以及它前面的那个服务 | 什么时候调哪个工具的说明 |
| 生成的测试落地 | 新仓库 | 团队已经在维护的两个自动化仓库 | 按那两个仓库规范写的测试 |

第四行我最喜欢。让 Agent 开一个 PR 听着小，其实不小：分支命名、识别远端、找 reviewer、扫密钥、API 拒绝时的手动处理。插件里已经有一个技能把这些全做了。我们告诉 Agent 去调它。这就是全部实现。

第二行有个额外收获。技能放在共享库里，另一个跑在完全不同 runtime 上的 Agent 产品能读到同一批文件。我们做了个 canary 验证：在某个技能里加一句话，第二天两个产品都能看到。复用不是 PPT 上的一页，是一个 diff。

## 当租户的代价

租户要守房东的规矩，不是自己的。

改一个技能要两个 MR：一个进共享库，一个把副本同步进插件，然后发布。我们的脚本要能跑在宿主承诺支持的最老 Python 上，比我笔记本上的老，这件事是发布当晚才发现的。命名要按宿主的规范。发布节奏是宿主的。这个月 marketplace 换了地方，我们跟着搬，通知用户重装。

这些都不是抱怨，是房租。另一条路是自己维护六个系统，而上面每一项成本，跟自己跑一个网关比都不算什么。

## 换来了什么

从第一张工单到别的团队能安装的版本，九周。两个人。几乎没有属于自己的、会半夜报警的基础设施。

还有一件没料到的事：因为我们拥有的东西全是文本，Agent 在几个家之间搬来搬去几乎没动过。插件换 marketplace 那次，指令一个字没改，用户拿到的是四行命令。拥有得少，和可迁移，原来是同一件事。

## 什么时候还是得自己做

复用是默认，不是法律。三种情况让我选择自己做。

房东说不，或者答应得不够快。一个你不能按自己节奏改的依赖，迟早会被你绕开；不如一开始就有意识地做这个决定。

你的用量会影响宿主。一个夜间任务持续冲击一个按交互式流量设计的网关，那不是复用，是好心的 DoS。

抽象和你的场景冲突了三次。我们有一个 bug 两个月里出现三次，每次看着都不相关，直到有人给它起了名字：共享组件里一条兜底路径，对我们的场景来说形状是错的。修法是上游把兜底修一次，而不是下游再加第四个特例。有时上游修不了，那就自己做。但先数到三。
