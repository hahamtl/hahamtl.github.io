先讲一个事故。一个负责评审需求文档的 Agent，去找它该评审的那份文档，搜索条件写得太宽，匹配到了一份不相关的旧草稿，然后很自信地把那份草稿改名成它本该找到的那个文档名。修复只改了一行搜索条件。但那份被改错名字的文档在系统里放了好几天，因为系统里没有任何东西能区分"Agent 写的名字"和"人写的名字"。

问题就在这里：Agent 没有做任何越权的事。它写下去的东西，在写下去的那一刻就成了事实。

## 两个不太好的答案

Agent 要往别人依赖的系统里写东西，通常有两种反应。

**收回权限。** Agent 只提建议，人来复制粘贴。安全，但 Agent 退化成一个很慢的自动补全，速度上省下来的全在复制那一步漏掉了。

**保留权限，把 prompt 写严。** 加规则、加例子、加"绝对不能做 X"。边际上有用，极端情况下失效，而极端情况恰恰是所有人记住的部分。

这两个答案有同一个前提：写入的那一刻就是成为事实的那一刻。我今年做的东西里，凡是有效的，都来自打破这个前提。

## 两个世界

任何共享系统都有两层，平时被当成一层。

一层是**存在**：一行记录、一个文件、一个页面、一张工单、一条消息。另一层是**算数**：报表读它，流水线跑它，团队照它行动，频道把它推给两百个人。

我现在的做法是：凡是 Agent 产出的东西，这两层必须分开。Agent 可以让东西存在，只有人能让它算数。具体实现就是 artifact 上一个状态字段，加上每个下游默认的过滤：草稿记录不进报表，草稿 PR 不触发评审，草稿消息留在私有频道。

## 到处都是同一个形状

一旦开始留意，会发现大多数系统里这个形状早就有了，只是没用满。

| Artifact | 草稿态 | "确认"是什么 | 谁在过滤草稿 |
|---|---|---|---|
| 代码改动 | draft PR，不指定 reviewer；测试没过的标 DO NOT MERGE | reviewer 点 ready | 评审队列、合并机器人 |
| 工单 | Agent 的文字进它自己的字段，不覆盖人写的描述 | 人把它合并进描述，或者忽略 | 读工单的人能看出谁写的 |
| 文档 | 建议模式，不直接改 | 文档 owner 接受 | 发布版本 |
| 数据记录 | 状态 = 未评审，归属 = Agent | 人改状态、接过归属 | 所有报表默认排除该状态 |
| 消息 | 发到私有频道或 thread | 人转发到团队频道 | 受众 |

这些都不需要新的基础设施。每一个只需要一个决定：哪个字段代表"草稿"；再加一个承诺：Agent 永远不碰翻转它的那两个字段。

## 一条我不得不放宽的规则

最清楚的案例是一个往团队共享的测试管理工具里创建测试用例的 Agent。这个工具是团队覆盖率数字的来源。写错一条不是笔误，是图表里的一句谎话，而人是照着图表做决策的。

第一版规则很直接：Agent 可以往已有的分组里加用例，但不能新建分组。安全。然后真实用户上来的第一周，到处是死路："没有匹配的分组，请找人处理。"最需要帮助的场景，恰好是规则禁止的场景。

我们把规则反过来了。Agent 可以建分组。但它建出来的分组自带报表本来就忽略的那个状态，归属写它自己。它不会把状态改成就绪，也不会改归属。这两个动作都留给人，都只需要一次点击。安全网从"不能做"变成了"没人看过就不算数"。覆盖率数字一点没变，Agent 的可用性完全不一样了。

## 三个配套的习惯

草稿默认要配上几个小习惯才站得住。

**写之前先列清单。** Agent 要建的每一条记录，一屏列完，一个词放行，一个词全部取消。人没法在事后审两百条草稿，但能在事前审一张十二行的清单。

**写完读回来。** 每次写入之后，把记录取回来，逐字段和原意对比。工具会出错，有时只是一点点，而一条和批准内容悄悄不一致的草稿，比没有草稿更糟。

**打上来源标记。** Agent 建的每个 artifact 都带一个"由 Agent 创建"的标记，放在没人会去编辑的字段里。几个月后有人问"这条哪来的"，答案在记录里，不在谁的记忆里。

## 代价

草稿需要有人认领。一个堆满未评审 Agent 产出的系统是一种新的垃圾，而且看起来像真工作的垃圾比空文件夹更糟。所以承诺是双向的：Agent 永远不确认，人要么确认要么删除。一个 sprint 内没人认领的草稿，直接清掉。
