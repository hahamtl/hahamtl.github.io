一个聊天 thread 里提到了两张工单。有人让 Agent 处理一下"那张 ticket"。Agent 选了它在这个 thread 里最早看到的那张，接着往下做。直到评论出现在错的工单上，才有人发现。

原来的规则很简单：thread 里第一次提到的工单，就是这个 thread 后续默认的工单。可以叫它锁。这个锁几个月来一直好用，这次失效是因为出现了第二张工单，而规则对这种情况没有任何说法。

## 第一版：让它更聪明

最直接的修法是让模型来选。看两张工单，读这条消息，挑一个用户最可能指的。多数情况下会选对。

产品负责人在开工前就否了，我觉得否得对。让 Agent 擅长猜"你说的是哪一张"是一个功能。它鼓励人说话含糊，也把本该由人做的决定挪给了模型。不管做得安全不安全，这不是我们想要的功能。

## 第二版：让它更严

第二版：thread 里只要出现过不止一张工单，就停下来问是哪一张。不猜，不加功能。上线了。

它失败的方式我没预料到。thread 里的对话历史从不重置。只要出现过第二张工单，哪怕只是顺口提了一句，哪怕是几周前，这个 thread 就永久地"有歧义"了。之后每一个请求都撞上拦截，被问同一个问题。大家干脆不用那些 thread 了。一个会触发但在整个对话生命周期里永远不会解除的安全机制，比它要替代的 bug 更糟，因为 bug 是偶尔的，拦截是永久的。

## 第三版：说出来

第三版，也是最后上线的：原来的锁一点不动，先提到的算。只加一件事：Agent 每次对某个 thread 的工单做操作时，在回复第一行写明它在处理哪一张。

"正在处理 ABC-123 · 修复导出超时"

改动就这么多。猜还是猜，但变成了看得见的猜。选错了，下一条消息就能纠正，而不是第二天在错的工单上被发现。从那以后再没出现过两张工单的问题没被当场看到的情况。

## 我记下的

| | 更聪明 | 更严 | 更响 |
|---|---|---|---|
| 逻辑改动 | 大 | 中 | 无 |
| 选错 | 更少，但仍然没声音 | 不可能，但一切都被拦住 | 频率不变，当场可见 |
| 副作用 | 鼓励含糊 | thread 永久卡死 | 每条回复多一行 |
| 结果 | 被否 | 回滚 | 上线 |

我原以为猜错的修法要么是猜得更准，要么是不猜。其实还有第三种：同样的猜，但说出来。在有人逐条读回复的实时对话里，这通常是最便宜也最安全的。
