刚开始在公司做智能体的时候，我理解的"智能体"只有一种：调一次模型，读答案，决定下一步，再调一次。之后一年，同一类系统我用三种完全不同的方式做了三遍，每一遍"智能体"这个词的含义都变了。

下面是精简版：变了什么，我会留下什么。

## 形态一：围着 API 写一个循环

第一套系统是一组住在聊天工具里的助手。一个读需求文档、指出遗漏，一个起草技术方案，一个开 pull request。掀开盖子，它们其实是同一个东西：对模型的一次无状态调用，外面包着我们自己写的代码。

"无状态"是关键。模型在两次调用之间什么都不记得，不会自己调工具，想停就停。于是外面那层代码得把其余所有事都补上：

- 一个对话存储，让下一次调用知道上一次说了什么
- 一个解析器，读模型的回答、决定该跑哪个工具
- 队列和重试，因为工具会失败、模型会超时
- 一个"做完了吗"的判断，用来结束循环

半年之后，仓库里大部分代码都是这层运行时，助手真正干的活反倒是上面薄薄一层。它能用，大家每天都在用，但每加一个能力都要穿过这层运行时，而这层运行时是我们谁都没打算去写的。

## 形态二：托管运行时

第二版把循环从我们的代码里挪了出去。一个托管的运行框架接手了原来手写的那些部分：会话、记忆、工具调用、身份，还有重启之后还能接着跑的长任务。我们带过去的只有指令、工具定义，以及几条"什么时候该停下来问人"的意见。

收益先体现在 diff 里：运行时目录几乎清空了。

让我意外的是精力去了哪里。没有循环可调了，整套系统的质量就只剩两件事：指令写得好不好，工具契约老不老实。一个声称"返回工单"却偶尔返回一个空壳的工具，以前算管道 bug；现在它是智能体的判断 bug，因为智能体相信了它。

代价是一条边界。出问题的时候，我们得透过别人的抽象去排查，状态也存在别人的存储里。当循环不是你要造的东西里最有意思的部分时，这个交换划得来。对我们来说确实不是。

## 形态三：一个文件夹里的文本

第三种是我之前想不到的。一个帮工程师规划和编写测试的智能体，不是以服务的形式部署，而是作为一个插件，装进他们本来就开着的编码助手里。没有服务器，没有队列。一个文件夹，里面是几份 markdown 指令、一张它可以调用的工具清单，外加一两个脚本。运行时就是这个人笔记本上的助手，凭据就是这个人自己的。

"部署"的含义随之改变。发新版本就是升一个版本号。权限就是用户自己已有的那些，不多一分。而且因为人就坐在旁边，智能体在每一次写入共享系统之前都可以停下来问一句。对共享系统来说，这正是你想要的行为。

它做不到的事也随之改变。它不会在夜里跑，不会自己去领一张工单。它的自主程度和一场对话一样，也就是说，没有。

## 并排看

| | 围着 API 的循环 | 托管运行时 | 文件夹里的文本 |
|---|---|---|---|
| 谁在跑循环 | 你的代码 | 托管框架 | 笔记本上的助手 |
| 状态存在哪 | 你的数据库 | 对方的存储 | 对话本身 |
| 你写什么 | 代码 | 指令 + 工具契约 | 指令 + 工具契约 + 几个脚本 |
| 怎么发布 | 部署一个服务 | 更新指令 | 升一个版本号 |
| 用谁的凭据 | 服务账号 | 服务账号或运行时的身份 | 用户本人的 |
| 能否无人值守 | 能，自己造 | 能 | 不能 |
| 人能否逐步确认 | 自己造才有 | 运行时支持暂停才有 | 默认就有 |
| 适合 | 单次转换，没有值得保存的状态 | 共享频道里的自主任务 | 每一步都该由人决定的工作 |

## 三次都留下的东西

把三种形态排成一行，有一件事很明显：我写的那部分一次比一次少，也一次比一次更像文字，从代码到配置再到指令。指令和工具契约比每一个循环都活得久，而且因为一直保持纯文本，在三种形态之间几乎原样搬过去。

<div class="callout">
<p><strong>我现在的规则：</strong>先把智能体写成文本，最后再选运行时。</p>
<ul>
<li>没人盯着也得跑、发生在共享频道里的工作：托管运行时。</li>
<li>每一步都该由人来决定的工作：把智能体放到这个人本来就在工作的地方。</li>
<li>一次性的转换、没有值得记住的状态：裸循环就够了。</li>
</ul>
</div>
