先说结论：过去一年，我做 Agent 的方式换了三次，每换一次，自己写的东西就少一截。从代码，到配置，到最后只剩几份说明文档。循环、状态、重试这些当初觉得是"核心"的部分，一个也没留下。留下来的是指令和工具契约。

下面把三种形态摊开讲，各自适合什么场景，最后给一条我现在的选型规则。

## 形态一：围着 API 手写一个循环

刚开始做的时候，我对 Agent 的理解就是一个 while 循环：调模型 → 看回答 → 决定下一步 → 再调。

第一套系统是挂在聊天工具里的一组助手。读 PRD 挑漏洞的、起草技术方案的、直接开 PR 的，各干各的。但底层其实是同一个东西：对模型的一次无状态调用，外面裹着我们自己写的一层代码。

问题就出在"无状态"三个字。模型两次调用之间什么都不记得，不会自己调工具，想停就停。它不管的事，全得我们自己兜底：

- 对话要存起来，下一轮才知道上一轮说了什么
- 模型的回答要有人解析，判断该调哪个工具
- 工具会挂、模型会超时，得有队列和重试
- 还得有个"是不是做完了"的判断来跳出循环

半年下来，仓库里的大头都是这一层。助手真正干活的逻辑反而只有薄薄一层。系统能用，大家天天用，但每加一个新能力都得从这层自研 runtime 里穿过去。而这层 runtime，当初谁都没打算写。

## 形态二：把循环交给托管 runtime

第二版直接把循环搬出了我们的代码。用了一个托管的 Agent runtime，之前手写的那一套它全包：会话、记忆、工具调用、身份、重启后还能接着跑的长任务。我们只需要带三样东西过去：指令、工具定义，以及几条"什么时候该停下来问人"的规矩。

收益在 diff 里一眼可见，runtime 目录基本清空。

但精力并没有省下来，只是换了地方。循环没得调了，整套系统的好坏就只取决于两件事：指令写得清不清楚，工具契约老不老实。举个例子，有个工具声称"返回工单详情"，但偶尔会返回一个空壳。以前这算管道 bug，修一下解析就完了；现在它变成了 Agent 的判断错误，因为 Agent 就是照着这个返回值往下推理的。

代价是多了一条边界。出问题要透过别人的抽象去查，状态在别人的存储里。如果循环本身不是你产品的核心，这个交换是值的。对我们来说，确实不是。

## 形态三：一个文件夹里的几份文本

第三种是我之前完全没料到的。

一个帮工程师做测试规划和写测试代码的 Agent，没有部署成服务，而是做成了一个插件，装进大家本来就开着的编码助手里。没有服务器，没有队列。整个 Agent 就是一个文件夹：几份 markdown 写指令，一张它允许调用的工具清单，再加一两个脚本。runtime 就是用户笔记本上的那个助手，凭据就是用户自己的。

"部署"的定义随之改变。发新版就是升个版本号。权限不用单独申请，用户有什么它就有什么，一分不多。最关键的是人就坐在旁边，所以它在每一次写入共享系统之前都可以停下来问一句"这样改，可以吗"。对共享系统来说，这正是你想要的。

它做不到的事也很明确：不会夜里自动跑，不会自己去领工单。自主程度和一场对话相当，也就是零。

## 三种形态并排比

| | 自己写循环 | 托管 runtime | 文件夹里的文本 |
|---|---|---|---|
| 循环谁跑 | 你的代码 | runtime | 用户本地的助手 |
| 状态在哪 | 你的数据库 | runtime 的存储 | 对话本身 |
| 你写什么 | 代码 | 指令 + 工具契约 | 指令 + 工具契约 + 几个脚本 |
| 怎么发版 | 部署服务 | 更新指令 | 升版本号 |
| 用谁的凭据 | 服务账号 | 服务账号或 runtime 身份 | 用户本人的 |
| 能否无人值守 | 能，但得自己造 | 能 | 不能 |
| 人能否逐步把关 | 自己造才有 | runtime 支持暂停才有 | 默认就有 |
| 适合 | 一次性转换，没有值得保存的状态 | 共享频道里的自主任务 | 每一步都该由人拍板的工作 |

## 唯一没变的东西

三种形态排成一行，最明显的一点是：我写的部分一次比一次少，也一次比一次更像"文字"而不是"代码"。指令和工具契约这两样东西，比任何一个循环都活得久，而且因为一直是纯文本，三次迁移基本原样搬过去。

<div class="callout">
<p><strong>我现在的选型规则：先把 Agent 写成文本，最后再挑 runtime。</strong></p>
<ul>
<li>没人盯着也得跑、发生在共享频道里的任务：托管 runtime。</li>
<li>每一步都该由人拍板的工作：把 Agent 放到这个人本来就在干活的地方。</li>
<li>一次性的转换、没有值得记住的状态：裸循环就够了。</li>
</ul>
</div>
