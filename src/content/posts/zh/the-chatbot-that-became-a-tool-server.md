我负责一个内部服务，用得最多的页面是一张很长的表单。QA、开发、产品经理都用它创建测试数据，做 demo、开发、测试都靠它。先选一个 partner，再填十几个字段，每个字段能填什么取决于这个 partner 支持什么：产品、货币、语言，还有一堆特殊情况。没人记得全。我自己也记不全，而这东西是我做的。

于是循环就成了：有人填错，报错看不懂，来问团队，团队查完回复，再去试。两边各花半天，换一行测试数据。

二月我在表单旁边加了个聊天面板。选好 partner，要么说"随便来一个"，要么用一句话描述需求，面板帮你把表单填上。Claude 通过 Bedrock API 调用，Spring Boot 后端，React 前端。从第一个 commit 到第三版原型，五周。

## 我以为自己在做什么

一个聊天机器人。我当时认为价值在对话本身：一层友好的界面，把"我要一个两人、带中转的预订"翻译成十四个字段值。

回头看，早期做的两件事比聊天重要得多。

**模型不决定事实。** 从第一天起分工就是：模型负责语言，代码负责事实。这个 partner 支持哪些货币？哪些产品？选了 cruise 之后哪些字段变成必填？这些答案来自读服务和缓存的普通代码，暴露给模型的是几个它可以调用的函数。函数里没有模型。模型的任务只有一件：理解人想要什么，然后调用对的那个函数。

二月的时候我不知道这个模式叫什么。代码里我管它们叫 "tools"，因为想不出别的名字。

**知识放在文件里，不放在代码里。** prompt、partner 备注、字段文档、直接跳过模型的 special flow（点个按钮不需要 LLM）：全是 YAML，启动时加载，用占位符注入 prompt。动机是保持代码干净，让非开发也能改措辞。后来没有第二个人改过，但这个结构留下来了。

再承认一个意外。开始的时候我不知道模型两次调用之间什么都不记得，是看着它忘事才发现的。解决办法是前端保存整段对话，每轮回传，后端每次从零重建 prompt。后来文档里写的是 "stateless by design"，其实是 stateless by discovery。不过事后看这是对的：没有东西要持久化，重启不会丢，每个请求都能单独测。

## 大家怎么用

有人在用。我们碰到的准确率问题，几乎没有一次是模型的问题。建议错的时候，错的是 context：某个 partner 的数据缺了，两个 partner 在一段对话里混在一起，或者事实在 prompt 里的排法让模型读错了。好的 context 进，好的答案出。这个规律在我后来做的每样东西上都成立。

## 转折

三月，情况变了。公司开始推终端里的编码助手。原来打开网页的人，现在待在一个自带模型的 CLI 里。网页表单里的聊天面板，看起来像第二个、更差的聊天窗口。

问题就很明显了：为什么知识要锁在我的 UI 后面？工具本来就是普通函数。partner 事实、字段规则、special flow 本来就是文本。这些都可以交给任何会说通用协议的助手。

于是同一个服务加了一个 MCP server。两周出 PoC。聊天面板一直在调的那些函数变成了 MCP 工具。YAML 里的知识变成了工具描述和助手动手前先读的指南。聊天面板原样保留，变成了众多客户端之一。

难点不在协议。难点是同事用三种不同的客户端，每种配置格式都不一样，而且大多数人对这些都不熟。安装必须是一条命令，否则推广会卡在 README 上。最后做成了一条命令。

半年后，这个 server 暴露几十个工具，创建测试数据只是其中一个领域。我后来在完全不同的 runtime 上做的 Agent，都把它当作进入测试系统的主入口。聊天面板还能用。有多少人还在用，我没有查过。

## 学到什么

| | 聊天面板 | MCP server |
|---|---|---|
| 入口 | 一个网页 | 任何会说协议的助手 |
| 对话由谁管 | 我的代码 | 用户本来就在用的助手 |
| 我要维护什么 | UI、prompt 组装、对话状态、工具、知识 | 工具、知识 |
| 加一个能力 | 面板里加一个流程 | 加一个工具，用文字描述 |
| 建造时间 | 五周 | 两周，在前者基础上 |

关键是第三行。聊天面板要我维护五样东西，server 只要两样，而这两样恰好是我最先做的，因为它们是唯一不需要模型就能测试的部分。

<div class="callout">
<p><strong>规则：</strong>做 AI 功能的时候，先找出那些"没有模型也依然成立"的部分：事实、规则、动作。把它们做成普通函数和普通文本。聊天只是一个客户端，客户端会来来去去。</p>
</div>
