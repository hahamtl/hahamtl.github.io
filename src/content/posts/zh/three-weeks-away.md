先说结论：休假回来发现系统换了骨架，第一天别碰工单。把这一天整个花在重建心智模型上：每个变更问四个问题，从零复现本地环境，最后能在白板上画出来。读 commit log 只能告诉你什么动了，告诉不了你别人现在默认了什么，而你会栽在那些默认上。

## 回来那天

三周产假，那种不开电脑的休假。

回来第一个早上，产品看着没变。同一个聊天界面，同一批助手，同样的名字。底下，二十来个已合并的变更换掉了整个后端。我之前写过的那个自己手写的循环没了，Agent 全跑在托管 runtime 上，每个 Agent 是一份声明式配置加一份人设文件。指令从应用仓库里搬了出去，共享仓库成了它们唯一的家。每个 Agent 和每个集成之间多了一个共享的 tools server。还有一套新的加载模型：指令文件的正文只在需要时才读。

全是好活，同事做的，每一步都有理由。只是这些理由没有一条在我脑子里。

## 补课的错误方式

第一反应很自然：读 change log，扫一遍合并的 MR，中午前开始干活。我这些年每次休假回来都这么干，一直管用。

它管用的前提是变更是叠加式的。模型变了它就不管用了。一条 commit message 告诉你什么挪了位置，不会告诉你作者现在默认了什么，而你会栽的正是那些默认。

## 我实际怎么做的

第一天整个给了这件事，一张工单没碰。

每个变更问四个问题，写下来：这是什么，为什么做，替掉了什么，如果我还信旧的那套会坏在哪。最后一个问题最值钱。前三个 MR 里都有，第四个哪儿都没有。

然后从零复现本地开发环境。不是"我机器上能跑，因为以前能跑"，而是干净 checkout，只按仓库里写的走，直到一个 Agent 在本地回答我。文档写错或漏掉的每一处，都是我的心智模型即将出错的地方。

一天结束，我能在白板上把它画出来。这就是标准。画不出来，读多少 commit 都不算补上。

## 一个只有这么做才会发现的 bug

新加载模型就是第四个问题的回报。

老 runtime 下，指令文件每次整个注入。大家也就这么写：顶上一段简短描述，真正的规则在下面，有时很下面。新 runtime 下，描述永远加载，正文只在模型觉得需要时才读。所有住在正文里的规则一下子都变成了可选项，没报错，没警告。文件一个字没改，改的是"什么一定会被读到"这个契约。

<a href="/img/back-from-leave/guaranteed.zh.svg" target="_blank" rel="noopener"><img src="/img/back-from-leave/guaranteed.zh.svg" alt="两种加载模型。旧的：整个指令文件每轮注入，靠下的硬规则一定被读到。新的：只有简短描述永远加载，正文按需取，同一条硬规则现在只是「可用」，经常根本没被读。修法是把承重的规则挪进永远加载的那层，把描述改成决定性的路由。"></a>

从 change log 里我看不出这个。那条记录写的是"技能正文渐进式加载"，准确，而且听着像优化。只因为我上午一直在问"如果我还信旧的会坏在哪"，才会冒出"哪些规则现在变成可选了"这个问题。

问题一旦有了名字，修法就是机械的：把承重的规则提到永远注入的那一层，把每段描述改成决定性的路由，告诉模型什么时候正文重要。一周后我和同事用一句埋进去的 canary 验证了共享仓库真的跨两个 Agent 产品生效：第二天两边都能看到。

## 读 log 和重建模型

| | 读 change log | 重建心智模型 |
|---|---|---|
| 时间 | 一小时 | 一天 |
| 学到 | 什么挪了 | 现在默认了什么 |
| 适合 | 叠加式变更 | 结构性变更 |
| 盲区 | 所有没变但含义变了的东西 | 几乎没有，前提是事后能画出来 |
| 检验 | 列表读完 | 能把每个决定讲给别人 |

## 想对当时的自己说的

三周足够一个系统换骨架。换了的话，回来的第一天不是浪费，是这个季度最划算的一天：每一小时都省下一个你会背几个月的错误默认。

<div class="callout">
<p><strong>规则：</strong>你不在的时候落地了结构性重写，回来先花一整天自己重建模型：每个变更四个问题，从零复现环境，画出来。另外，文本底下的加载机制一变，就去查什么是「一定会读」，不是什么「可以读到」。</p>
